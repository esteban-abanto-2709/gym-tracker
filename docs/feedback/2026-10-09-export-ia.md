# Feedback: AI export (2026-10-09)

External review, done with another AI, of the export's test file (RM-021): a
`.md` with profile, body measurements in CSV, reading conventions and one row
per set in CSV. The question was whether an AI can read it and answer "how am I
doing?" without making things up or misreading.

## Verdict

**It works as it is for the first version.** It explains what the data
represents, keeps the detail needed to verify conclusions and allows answering
real questions about progress. None of the improvements below is blocking; the
only condition is that what's exported faithfully reflects what's stored.

## What already works

- One row per set: lets you compare loads and reps across sessions.
- Telling working sets, warm-ups and ramps apart: avoids counting the warm-up
  as volume.
- Explicit units and conventions (barbell total, dumbbell per unit).
- Dated body measurements, date and time per set, and original notes.
- Markdown with CSV blocks: readable instructions + tabular data.

## What questions it supports today

| Question | Support |
|---|---|
| Am I progressing in my exercises? | Good |
| How much and how often do I train? | Good, with caveats (double or incomplete sessions) |
| How is my body weight changing? | Partial: describes the change, not whether it's fat or muscle |
| Do I train with enough intensity? | Insufficient: perceived effort is missing |
| Is my routine well designed? | Partial: goals and context are missing |

## Proposed improvements and status

Ordered by impact according to the feedback. The stance is the project's
decision, not the review's. **Status** says what's already applied and where;
when a new improvement is applied, it's updated here.

| Improvement | What it solves | Stance | Status |
|---|---|---|---|
| Clear empty-value policy | "Empty" mixed *doesn't apply* and *wasn't logged*. In measurements, an empty value isn't a drop and doesn't carry the previous value. | Do now: it's text. | **Applied** (RM-021): one rule per case in sets, equipment and measurements. |
| Period coverage | Tell the requested range apart from the range with records; a day without sets doesn't prove rest. | Do now: one line. | **Applied** (RM-021): requested period, first and last day with sets, days and a notice. |
| Format version | So a future export with another meaning isn't confused with this one. | Do now: one line. | **Applied** (RM-021): `Formato: gym-tracker-export v1`. |
| Rest between sets | Context for performance drops. | Already deducible from each set's time. | **Applied** (RM-021): stated in the conventions. |

Beyond what was asked, the RM-021 version adds age (from the birth date) and
the period's body measurements with the last earlier one as a starting point
(WL-071).

## Data problems it noticed

- Ramps of the same exercise with different equipment on the same day
  (dumbbell and barbell): looks like a logging mistake, not a variant change.
- Two routines on the same day with few sets: in this case they were test sets
  in the development environment.
- Weights with odd decimals (`11.3`, `18.15`): they're pounds converted to kg;
  see WL-009.

## How to validate each version

Use the same file with five questions: overall progress, progress of one
exercise, volume distribution, body changes and what to change next period.
Check the numbers by hand and that the answers acknowledge what the file
doesn't prove. If it answers confidently about what isn't there, strengthen the
conventions; if it asks for too many clarifications, improve the structure.
